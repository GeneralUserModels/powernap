You are building a self-contained mini-web-app that the user will open, edit, refine, and act from. The app must be useful in one of two ways:

1. **Control center:** the tada itself is the main project surface. The user manages the trip in it, edits the email draft in it, refines the review in it, tracks the decision in it, and acts from it.
2. **Transfer surface:** when the real work belongs in another app (spreadsheet, document editor, project tracker, calendar, design tool, codebase, etc.), the tada prepares the information so the user can move it there cleanly. Provide copy/export actions for the exact structured content that belongs in that external app, such as TSV/CSV rows for a spreadsheet, Markdown for a doc, an email body, calendar details, checklist text, or a concise prompt/spec.

Either way, the tada is not a passive document. It is either the place to manage the topic or the best launchpad for moving prepared information into the app where the user will execute the project.

Final artifact: a folder at `{output_dir}` containing an `index.html` + `styles.css` + `app.js`, plus copied-in `base.css` and `components.js` from the shared library. The renderer loads `index.html` inside a sandboxed iframe.

## App Contract

The artifact must be:
- **Self-contained.** Everything needed to use it lives in `{output_dir}/`: HTML, CSS, JS, and any data the agent prepares (inline in `app.js` as `const DATA = ...`).
- **Stateful.** Every editable surface (textarea, input, checkbox, sort order, expanded state) persists across reloads via `PN.useDraft` / `PN.useChecklist` (localStorage-backed, scoped to the moment's slug).
- **Operable.** The user either does the work in the app — checks items off, edits drafts, marks decisions, triggers actions — or can copy/download the prepared content into the external app where the work should happen.
- **Pre-filled with the actual content.** The value comes from the prepared draft / comparison / recommendation, not from the UI. Do not ship an empty form for the user to fill — fill it from the sources, then let them edit.
- **Copy/export-first for external workflows.** If a spreadsheet, document, issue tracker, design tool, or other app is clearly the better execution surface, include visible copy/download buttons using `PN.Actions.copyToClipboard` or `PN.Actions.downloadFile`. Format copied content for direct paste into that app (for example tab-separated rows for spreadsheets, Markdown for docs, or a compact spec for a project tool).
- **Preparation-only on outbound actions.** The app code never sends email, submits a form, posts publicly, deploys, books, buys, applies, cancels, or changes account settings on its own. Any outbound effect must go through `PN.Actions.*` and happen only after an explicit user click on a visible button.

## Decide the Artifact Shape First

Before picking a template, decide what the user is actually doing in this app. Most tadas are not dashboards. Match the candidate's `desired_artifact` to one of these shapes:

- **Email / message draft** → editable subject + body fields backed by `PN.useDraft`; recipient/context chips at the top; a "Send" button that calls `PN.Actions.sendEmail({{to, subject, body}})`; a "Copy" fallback via `PN.Actions.copyToClipboard`.
- **Paper / document review** → side-by-side: source bullets on the left, editable review body on the right; per-comment severity selectors; a "Copy review" button.
- **Briefing for a meeting / new person** → collapsible person/topic sections; a "questions to ask" editable list; a per-topic "ready" checkbox.
- **Comparison / decision** → table with criteria rows, options as columns; pre-filled recommendation banner at the top; editable weights so the user can re-rank by changing what they care about.
- **Trip / itinerary** → editable day-by-day plan; per-day notes textarea (`PN.useDraft`); booked-vs-pending checkboxes (`PN.useChecklist`); "open in maps" via `PN.Actions.openExternal`.
- **Recurring digest / research feed** → today's content prominently; a small "what's new since last run" diff; editable "follow-ups" carry-over textarea.
- **Checklist / runbook** (only when the artifact really is a list of user actions) → `PN.useChecklist` for state; group sections with `PN.GlassCard`.
- **Long-form recap / advisory / spec** → linear sections, optional timeline, optional action items.
- **Status overview with real metrics** → KPI pills + filterable cards. Only when there are genuine numbers to track (counts, dollar amounts, deadlines, completion %).

When an external app is the better execution surface, choose a shape that makes transfer effortless rather than pretending the tada should replace that tool. Examples: a spreadsheet-ready table with a "Copy TSV" button, a document outline with "Copy Markdown", a project plan with "Copy tasks", or a meeting prep surface with "Copy agenda".

- `.section-head` — header inside a card (title left + badge/action right).

## PN.* Component & Action API

Components (loaded as `const { PageHeader, GlassCard, ... } = PN`):

- `PageHeader({{title, subtitle, badges, status}})` — page title row.
- `GlassCard({{delay, className, style, onClick, children}})` — primary container.
- `Badge({{text, type}})` / `BadgeRow({{badges}})` — labels (type: `success|warning|danger`).
- `StatRow({{stats: [{{value,label,highlight}}]}})` — KPI pills.
- `SearchInput({{value, onChange, placeholder}})` — controlled search.
- `FilterBar({{filters, active, onChange}})` / `TabBar({{tabs, active, onChange}})` — nav.
- `ItemCard({{title, subtitle, description, badges, meta, url, onClick}})` — content card.
- `EmptyState({{message}})` / `ResultCount({{count, total}})` — small UI bits.

Hooks:

- `PN.useFilter(items, key, activeFilter)` — filter by `item[key] === activeFilter`.
- `PN.useSearch(items, fields, query)` — case-insensitive search across fields.
- `PN.useDraft(key, initial)` → `[value, setValue]` — localStorage-backed draft persistence, scoped to this moment's slug. Use for every editable surface.
- `PN.useChecklist(key, items)` → `[state, toggle, reset]` — `items` is `[{{id, label, initialDone?}}]`; `state` is an **object map** `{{[id]: bool}}` (NOT an array). Check with `state[id]` / `!!state[id]`; never `state.includes(id)`. `toggle(id)` flips one; `reset()` clears all.

Outbound actions (postMessage to the renderer, returns a promise):

- `PN.Actions.sendEmail({{to, cc?, subject, body}})`
- `PN.Actions.addCalendarEvent({{title, start, end?, location?, notes?}})`
- `PN.Actions.saveToMemory({{title, body, category?}})`
- `PN.Actions.markComplete({{reason?}})`
- `PN.Actions.openExternal(url)`
- `PN.Actions.downloadFile({{filename, content, mime?}})`
- `PN.Actions.copyToClipboard(text)`

Some actions are stubbed in the current renderer (the helper returns `{{ok:false, error:"not_implemented"}}`) — show a small toast in that case so the user knows the contract is wired but the server piece is pending. `copyToClipboard`, `openExternal`, `downloadFile`, `markComplete` are fully wired today.

## Verify Before Stopping (mandatory)

Browser-side JS runs as classic `<script>` tags in a shared global scope. A single SyntaxError in any file leaves the iframe blank. Run these checks before your final stop:

1. **Syntax-check every JS file you wrote or copied.** For each of `app.js`, `components.js`, and any other `.js` you produced, run:

   ```bash
   node --check {output_dir}/app.js
   node --check {output_dir}/components.js
   ```

   If a check fails, fix the file and re-run until it passes. Do not stop on a failing check.

2. **Do not redeclare globals that `components.js` already declares.** `components.js` declares these at file scope and they become global because every script is a classic (non-module) `<script>`:

   - `const h = React.createElement;`
   - `const { useState, useCallback, useMemo, useEffect } = React;`

   If your `app.js` (or any other script) repeats any of those `const`/`let`/`var` declarations, the browser throws `Uncaught SyntaxError: Identifier 'h' has already been declared` and the app never mounts. In `app.js` just use `h(...)`, `useState(...)`, etc. directly — they are already in scope. Only destructure what is *not* already global (e.g. `const { PageHeader, GlassCard, useDraft, Actions } = PN;` is fine — `PN.*` symbols are not globals).

3. **Sanity-check the load order in `index.html`.** Order must be: React UMD → ReactDOM UMD → `components.js` → `app.js`. If `app.js` runs before `components.js`, every `PN.*` reference is undefined.

4. **Do not install npm packages and do not import bare modules.** Everything ships via the React UMD `<script>` tags already in the template's `index.html` plus our `components.js`. No `import`, no `require`, no `package.json`, no `node_modules` — `node --check` is purely a syntax pass, not a build step.

If any check fails, fix it before writing your final status. A blank iframe is worse than no app.
